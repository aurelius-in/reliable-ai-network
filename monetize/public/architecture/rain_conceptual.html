0.1Term mapping

TermWhat it isWhat it is not
Creation The creator’s product or offer context (title, description, type) that tools operate on Not a deployed app instance; not a Stripe product
Tool A journey step that produces or records a durable asset (often via Grok) Not an unconstrained chatbot; not a billing action
Generated asset Versioned JSON (or structured) output stored for a creation and tool type Not ephemeral chat history; not the source of entitlement
Tier Entitlement floor: Starter, Growth, or Pro, synced from Stripe Not a feature flag set by the model

Reasoning layer Grok JSON completions used by tool APIs under app-owned prompts Not the authority for money, identity, or RLS
Counter First-party analytics pipeline into analytics_events Not a third-party marketing pixel substitute for product truth

01Purpose

This document states why the system exists, who it serves, which nouns matter, and how value moves at a conceptual level. It is written so an investor or architecture reviewer can judge whether the product was designed with clear boundaries before reading APIs or schemas.

  • Separate enterprise intent from technology choices.
  • Make authority boundaries explicit (billing, identity, AI).
  • Give a stable vocabulary for Logical and Implementable docs.

02Enterprise viewpoint

2.1 Objectives

  1. Help a creator define a monetizable creation and progress through a coherent tool journey.
  2. Monetize RAIN itself via transparent subscription tiers with a 30-day trial.
  3. Keep AI productive and bounded: structured assets, not autonomous business decisions.
  4. Grow through referrals and checklist nurture without dark patterns (unsubscribe, clear Terms).
  5. Operate with an as-built stack that is inspectable: Auth, Postgres RLS, Stripe webhooks, signed APIs.

2.2 Constraints and principles

PrincipleImplication
Billing is source of truthProfile tier/status follows Stripe events, not UI optimism
AI proposes, app disposesModel outputs become assets only after API validation and persist rules
Least privilege data accessUser data via RLS; service role only for webhooks, track, admin ops
Journey over toolbox chaosTools are ordered; next-best-action guides progress
Honest commercial surfaceTrial end charge, auto-renew, referral rules stated in product and Terms

2.3 Stakeholders and roles

RoleCares aboutDoesDoes not
Creator (subscriber) Speed to a priced offer and buyers Runs tools, manages billing, refers peers Does not administer platform infra
Prospect (checklist lead) Whether RAIN is worth a trial Submits checkup; receives nurture Does not access dashboard tools until signup
Operator (RAIN) Conversion, reliability, abuse Reads Counter/admin; configures Stripe/Resend Does not silently invent testimonials or hide pricing
Architecture critic / investor Boundaries, durability, AI honesty Reads this doc set Does not need production secrets

2.4 What the system does NOT do (today)

  • Does not process payments between the creator and their end customers.
  • Does not claim the model “knows” live market truth without enrichment sources.
  • Does not grant tier access from a prompt response.
  • Does not replace legal counsel, tax advice, or securities advice for the creator’s business.

05Narrative framing

Three modes of using the platform, analogous to configure / operate / govern in industrial systems:

Configure

Sign up, choose tier, create the Creation, set referral attribution. Establishes identity and commercial context.

Operate

Run journey tools, generate assets, pull leads, track milestones. Day-to-day creator work.

Govern

Billing portal, cancel/upgrade, unsubscribe from nurture, Terms/Privacy, operator Counter views. Control and accountability.

Critical semantics

Trial users are entitled at Pro during trial; after trial, paid tier and invoice.payment_succeeded drive commercial reality including referrals.
